# Talking about Pulse

Notes for myself. The goal is not to recite these — it is to have thought each
one through so the answer comes out naturally.

---

## "Walk me through what you built"

*Two minutes. Lead with the problem, not the tech.*

Pulse is an uptime monitoring service. It checks customer websites every thirty
seconds from outside their network, and when something breaks it opens an
incident, alerts them within a minute, and updates their public status page.

It's five Go services sharing a Postgres database and a Redis queue, three
React frontends, running on EKS in Canada. Terraform builds the whole
environment from nothing in about eighteen minutes. CI runs tests, lints,
scans containers for vulnerabilities, and publishes to two registries.

The interesting part isn't any single piece — it's that it's a complete
product. Billing with Stripe, teams with permissions, GDPR data export,
account deletion. I wanted to build the thing companies actually run, not a
demo.

---

## "Is it microservices?"

*This is a trap question. The honest answer is stronger than the flattering one.*

No, and I'd push back on calling it that. Five services, but they share one
database — real microservices own their data.

It's a modular monolith split by workload. Each service was separated for a
specific reason:

- The scheduler must be exactly one copy, or checks run twice
- Workers scale with customer count, independently of web traffic
- The notifier is separate so a slow email provider can't delay checks
- Retention runs heavy periodic jobs that shouldn't compete with requests

If I'd given each its own database, I'd have distributed transactions and
eventual consistency to reason about, for a product that gains nothing from
either.

**Follow-up — "When would you split the database?"**
When one service needs to scale its *data* independently, not just its compute.
Check results are the only table growing fast. If that became a problem, that
table moves to a time-series store first — not the whole thing into five
databases.

## "Tell me about a bug that was hard to find"

*Three good ones. Pick based on what they're probing for.*

### The security group that looked right

All the backend services were crash-looping in EKS. The frontends were fine.
Logs were completely empty.

The security group said "allow Postgres from the node security group," which
read as correct. But with the AWS VPC CNI, every pod gets its own network
interface carrying the *cluster* security group that EKS manages — not the one
attached to the nodes. So the rule allowed the kubelet and blocked the actual
application.

It showed up as a connection timeout rather than a refusal, because the packets
were being dropped rather than rejected — which pointed me away from the real
cause for a while.

**What I took from it:** timeout means dropped, refused means rejected, and
the difference tells you whether you're looking at a firewall or a service.

### The migration that deleted its own evidence

Same incident, second layer. The Helm chart ran migrations as a hook with
`hook-delete-policy: hook-succeeded`, so the job removed itself after running.

When the app failed for the networking reason above, there was no job to
inspect and no way to tell whether migrations had run at all. I spent longer
than I should have on the wrong hypothesis.

I changed the policy so the job persists until the next deploy replaces it.

**What I took from it:** cleaning up successful runs is fine until the failure
is somewhere else and you need to prove what already happened.

### The version that expired

`terraform apply` failed creating RDS: Postgres 16.4 didn't exist. It had — AWS
retired that minor version between when I wrote the config and when I ran it.

I'd pinned an exact minor version thinking that was the careful choice. It's
actually a time bomb, because the provider retires minors on their own
schedule. I now pin the major and let minor upgrades happen in the maintenance
window; major upgrades stay deliberate because they can break queries.

## "How do you handle secrets?"

The database password is generated by Terraform and written to AWS Secrets
Manager. It is never in a config file, a Helm value, or a CI log.

Pods get it through External Secrets, which authenticates using IRSA — an IAM
role bound to one specific service account in one specific namespace. The role
can only read secrets under `pulse/prod/*`, not the whole account.

**Why not just mount an AWS access key?** Because then the key has to be
rotated by hand, and anyone who can read that Secret has it. IRSA tokens are
issued and rotated by the cluster automatically and are scoped far tighter.

**Follow-up — "What if someone gets shell on a pod?"**
They'd have that pod's permissions, which is read access to this project's
secrets — not the node's role, and not the whole account. I also enforce IMDSv2
with a hop limit of one, so a container can't reach the instance metadata
service to steal the node's credentials.

## "How does deployment work, and what's missing?"

CI builds nine images, scans each with Trivy, and publishes to GHCR and ECR
tagged by commit. Deployment is `helm upgrade` with a values file per
environment.

**What's missing is GitOps.** Right now I deploy from my laptop. The cluster
doesn't reconcile itself, so if someone changed something by hand, nothing
would correct it or even notice.

ArgoCD is the next thing I'd add — the repo becomes the source of truth and
the cluster continuously reconciles toward it. I understand the pattern; I
haven't implemented it here yet, and I'd rather say that than pretend.

## "What would you do differently?"

**Structured startup failures.** My services exit before logging when they
can't reach the database. That turned a small networking mistake into an hour
of debugging. Every service should log what it was trying to reach and why it
gave up before it dies. This is the first thing I'd fix.

**Test the security groups, not just write them.** I'd add a check that runs
after deploy and proves a pod can actually reach the database, rather than
finding out because everything crash-loops.

**Own the teardown path from day one.** The load balancer controller creates
resources Terraform doesn't know about. My first `terraform destroy` failed
three times on leftovers. That's now a Make target that removes the Helm
release first.

## "Why isn't this production-ready?"

*Answer this honestly. The list is the point.*

- **Single region.** An AWS regional outage takes it down — the worst possible
  moment for a monitoring service to be unavailable.
- **Nothing watches Pulse.** If it stops checking, nobody finds out. A
  monitoring product that can't detect its own failure is the classic problem in
  this category. The fix is an external heartbeat.
- **No SLOs.** I have no defined target for what "working" means, so I can't
  say whether a bad day was acceptable.
- **Rate limiting counts per pod**, so three replicas means three times the
  intended limit. Needs a shared counter in Redis.
- **Tokens can't be revoked early.** Removing someone's admin role doesn't take
  effect until their 24-hour token expires.
- **Single-AZ database, no automatic failover.** A deliberate cost decision for
  a project with no customers, and the first thing I'd change for one with them.

## The question behind the questions

Most of these are really asking: *has this person operated something, or only
built it?*

The evidence that I have: I broke it, and the ways it broke were specific.
Pods that couldn't reach a database through a security group that read
correctly. A version AWS retired underneath me. A teardown that failed because
two systems each owned half the resources.

You don't hit those reading tutorials.
